# 최소 구현

2026-11-12. 종이 위의 설계가 확인하지 못한 것을 확인하기 위한 코드다. 제품이 아니다.

## 1. 목적

[13](13-형식-시험-나머지-열두-영역.md)에서 남긴 세 질문에 답한다.

1. 심판과 인물 호출이 장부 형식의 제안을 안정적으로 내는가.
2. 문맥 조립이 정보를 격리하는가.
3. 한 턴이 50원, 15초 안에 드는가.

## 2. 만든 것

| 파일 | 내용 |
| --- | --- |
| `raindec/ledger.py` | 장부: 개체, 사실, 정의, 사건, 시야. 위치 관계, 계승, 되감기 |
| `raindec/conditions.py` | 조건 언어의 계산(참/거짓/모름)과 되읽기 |
| `raindec/scenario.py` | 시나리오 읽기, 변수 결정, 세션 개설, 명백한 지각 |
| `raindec/turn.py` | 한 턴: 심판 → 판정 → 인물(병렬) → 서술자 → 마감 |
| `raindec/llm.py` | Gemini 호출, 토큰·시간·비용 측정, 시험용 가짜 호출 |
| `raindec/common.yaml` | 공용 사전 최소판 (정의 30여 개) |
| `scenarios/객잔.yaml` | 시험용 시나리오. 숨겨진 진실 셋(주모의 비밀, 척후의 정체, 열쇠의 위치) |
| `play.py` | 터미널 플레이와 측정 |
| `tests/` | 시험 16개 |

- 언어는 **Python**으로 정했다. 디스코드 봇과 Gemini SDK의 관례를 따른 임시 결정이며 사용자 확인이 필요하다.
- 실행 방법은 저장소의 `README.md`에 있다.

## 3. LLM 없이 확인된 것

시험 16개가 통과한다. 가짜 호출을 쓰므로 LLM의 품질과는 무관하고, **코드가 보장하는 것**만 확인한다.

| 확인한 것 | 내용 |
| --- | --- |
| 위치는 하나의 관계 | 검 → 인물 → 지점 → 장소 → 건물의 사슬에서 "어느 장소에 있나", "누가 지녔나"가 나온다 |
| 계승 | 장소가 상위 장소와 분류 헤드에서 분위기를 물려받는다. 자기 값이 우선한다 |
| 변수 | 열쇠의 위치가 씨앗마다 달라지고, 같은 씨앗은 같은 세계를 만든다 |
| 검사 | 정의에 없는 속성, 등급에 없는 값은 기록되지 않는다. 묶음 중 하나라도 틀리면 전부 무효 |
| 되감기 | 사건 기록을 앞까지만 쌓으면 이전 세계가 나온다 |
| 진실과 시야의 분리 | PC는 척후의 겉모습은 알지만 정체는 모른다. 주모는 안다 |
| 조건 언어 | 낱개, 묶기, 어떤, 시야 한정, 모름의 세 값 계산, 한국어 되읽기 |
| 제안의 검사 | 심판의 제안 일곱 중 넷(없는 속성, 주권 침범, 없는 등급, 없는 장소)이 거부되고 셋이 반영된다 |
| **정보 격리** | 인물 호출의 문맥에 남의 비밀·목표·품속의 물건·PC의 내면이 없다. 서술자의 문맥에 진실과 속마음이 없다 |
| 원자성 | 서술자 호출이 실패하면 그 턴의 어떤 변화도 기록되지 않는다 |
| 세계 밖의 말 | 규칙 질문은 세계의 시간과 기록을 움직이지 않는다 |

### 시험이 잡아낸 누설

- 처음 구현에서는 **서랍 속의 열쇠가 PC의 시야에 들어갔다.** "같은 장소에 있는 것은 보인다"는 규칙이 닫힌 용기 속까지 보이게 했다.
- 격리 시험이 서술자 문맥에서 열쇠를 발견해 드러났다. "그냥 보이는 자리에 있는가"를 따로 계산하도록 고쳤다
  (닫힌 것 속, 남의 품속, 숨겨진 것은 보이지 않는다).
- 교훈: 격리는 문맥 조립 코드의 정확성에 달려 있고, **시험으로만 지켜진다.** 격리 시험은 시나리오마다 자동으로 돌아야 한다.

## 4. 아직 확인하지 못한 것

Gemini API 키가 없어 실제 호출을 하지 못했다. 다음은 **전부 미확인**이다.

- 심판이 스키마대로, 정의된 속성과 등급만으로 제안을 내는 비율
- 인물의 반응과 대사의 품질, 서술의 품질
- 서술자가 재료에 없는 것을 얼마나 지어내는가, PC의 내면을 얼마나 침범하는가
- 턴당 실제 비용과 대기 시간
- 쓸 수 있는 모델의 정확한 이름 (`play.py --models`로 확인)

측정 방법은 준비되어 있다: `python play.py --bench`가 선언 여섯 개(관찰, 대화, 내면을 밝힌 관찰, 잠긴 문 열기,
세계에 대한 단정, 대치)를 돌려 호출별 시간·토큰·비용과 거부된 제안을 낸다.

## 5. 구현하지 않은 것

- 디스코드 연결, 상태판
- 기제의 실행 (게이지의 변화, 시계, 전이, 예약, 위치 제약, 변환)
- 규칙의 실행 (조건 계산기는 있으나 규칙을 발동시키는 부분이 없다)
- 틀 찍어내기 (시나리오의 변수만 구현)
- 연출가, 화면 밖 세계의 진행
- 인물의 행동이 세계를 바꾸는 처리 (지금은 기분만 반영하고 의도는 기록만 한다)
- 경계 사례의 지각을 심판이 판단해 기록하는 처리 (지금은 심판이 인물별 지각 내용을 글로 적는다)
- 서술이 지어낸 세부의 처리 (P4, 보류 중)
- 판정 체계 (수치는 임시 값)

## 6. 구현하며 알게 된 설계상의 문제

- **심판의 "PC지각" 필드가 격리의 구멍이다.** 심판은 진실을 보고 "PC가 지각한 결과"를 글로 쓴다.
  여기에 숨겨진 사실을 적으면 서술자로 넘어간다. 지금은 지시로만 막고 있어 "구조로 보장한다"는 원칙에 어긋난다.
  대안: 심판은 변화만 제안하고, PC가 지각한 것은 코드가 변화에서 계산한다. 다만 "자물쇠가 꿈쩍도 하지 않는다" 같은
  **변화 없는 결과**를 전할 길이 필요하다.
- **심판이 인물별 지각 내용을 글로 쓰는 것도 같은 구멍이다.** 인물에게 넘어가는 유일한 자유 문장이다.
- **개체 이름이 곧 식별자다.** `뒷문_열쇠` 같은 이름이 문맥에 그대로 보인다. 이름 자체가 정보를 흘릴 수 있다.
